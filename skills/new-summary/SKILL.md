# Сборка нового Summary

## Назначение

Собери короткое Summary для члена инвестиционного комитета, который впервые
видит инициативу. Читатель должен быстро понять:

- что это за инициатива;
- на какой стадии она находится;
- какие обязательные элементы документа присутствуют или отсутствуют;
- что подтверждено имеющимися доказательствами;
- что пока подтверждено недостаточно;
- какие проблемы критичны для обсуждения.

Не принимай формальное решение за инвестиционный комитет. Не используй единый
вердикт, GO/NO-GO, `Need Evidence` или общий светофор инициативы.

## Входные данные

На вход передаются:

1. Название инициативы.
2. Определённая стадия документа.
3. Полный структурированный результат продуктового анализа Gate Challenger,
   включая обязательные элементы, доказательства, выводы и критические риски.
4. Полный структурированный результат финансового анализа IC Review, включая
   executive brief, ключевые выводы, риски и data gaps.
5. Исходный документ в формате word, PDF или MD.
Пользователь может передавать несколько документов. Важно брать информацию из главного документа (обычно в нем содержится несколько FAQ).
Если ты видишь документы в формате .Excel, можешь игнорировать их.

Не запрашивай отдельный вывод Devil's Advocate. В текущем процессе Devil's
Advocate выполняется до Gate Challenger, а его подтверждённые сигналы могут
быть включены в продуктовый анализ Gate Challenger как Layer 4 context.
Повторная прямая передача Devil's Advocate может задвоить одни и те же выводы.

Используй только факты и выводы из переданных результатов. Не добавляй новые
факты, цифры, причинно-следственные связи, оценки или доказательства.

Исходный документ используй только для улучшения читаемости раздела Контекст инициативы и для сбора метрик в таблицу Traction Summary
Не используй собственный анализ исходного документа для дополнительного нахожденя выводов.
Все выводы по цифрам и проблемам бери только из полных структурированных продуктовых и финансовых анализов.

## Язык результата

- Пиши результаты на двух языках в одном документе.
- Не чередуй языки внутри отдельных разделов. Сначала выведи полную версию
  Summary на английском языке со всеми обязательными разделами, затем
  выведи полную версию Summary на русском языке со всеми обязательными разделами.
- При формировании русской версии пиши весь результат на естественном русском языке.
- При формировании английской версии пиши весь результат на естественном английском
  языке без кириллицы, кроме подтверждённых собственных названий, для которых
  нельзя достоверно определить латинское написание.
- Русская и английская версии формируются независимо из одинаковых входных
  результатов Gate Challenger и IC Review и исходного документа. Не переводи одну готовую версию в
  другую и не используй текст другой версии как источник.
- В обеих версиях сохраняй одинаковые факты, числа, статусы обязательных
  элементов, количество смысловых тезисов и порядок разделов.

## Общие правила

- Используй простой деловой язык. Не усложняй его необъясненными аббривиатурами. Объясняй значение цифр, если цифра нужна для
  понимания вывода. Не пиши общих фраз, если они не подтверждены цифрами из документа, например, фраза "однако, большая часть заявленного эффекта"
  не должна употребляться, если ты не можешь точно сказать, большая часть - это сколько в значении метрики.
- Не делай предложения длинными, одно предложение - одна законченная мысль, посвященная какому-то конкретному предмету/метрике/цифре.
- Не выдумывай метрики от себя и не смешивай текущие.
- Не начинай Summary с отдельных метрик, процентов или финансовых показателей.
- Не дублируй один вывод в нескольких разделах, в соответвии с правилами раздела "Строгие правила для избегания дублирования информации в разделах".
- Не смешивай проверку наличия обязательных элементов с оценкой качества
  продуктовой или финансовой аргументации.
- Не создавай отдельные разделы продуктового, финансового или стратегического анализа.
- Не добавляй цель встречи.
- Не добавляй рекомендации, план исправлений или раздел «Что сделать перед защитой».
- Не превращай проблему в рекомендацию. Опиши суть проблемы, чем это подтверждено и что нужно обсудить.
- Если для необязательного раздела нет подтверждённой информации, не выдумывай
  содержание и не заполняй его общими словами.
- Максимальный объём всего Summary — 1 500 слов.
- Если ты нашел одинаковые по сути выводы в результатах Gate Challenger и IC Review, оставь вывод только Gate Challenger.
- Сохраняй одинаковый порядок разделов во всех отчётах.
- Когда будешь формировать Summary в документ, используй конструкцию "AI Summary" + "название инициативы".
Например, для инициативы с названием "From People to People" название Summary должно звучать так: "AI Summary From People to People"
- Информацию в разделе "Обязательные элементы документа" выводи с красной строки относительно заголовка (
делай небольшой, одинаковый для всех подразделов отступ вправо относительно заголовка раздела).
- Между разделами добавь дополнительный отступ, одинаковый для всех разделов, чтобы визуально разграничить разделы.
- В веб-версии выровни левый край переключателя языка по левому краю панели вкладок; заголовки разделов сделай на 2 пункта крупнее текущего размера.

## Строгие правила для избегания дублирования информации в разделах

- Каждый смысловой вывод должен иметь один primary home. Например, если факт уже использован как доказательство в "Обязательных элементах документа", он не может повторяться в "Выявленных проблемах". Это правило применимо для фактов из любых разделов.
- порядок владения информацией для разных разделов и подразделов:
    1. Обязательные элементы документа — отдельные правила по наполнению представлены для каждого подраздела (Отдельный раздел)
    2. Выявленные проблемы — decision-critical проблемы, подсвеченные во входных данных. (Отдельный раздел)

## Порядок разделов

Выводи разделы только в следующем порядке:

1. Название инициативы.
2. Стадия инициативы.
3. Traction Summary.
4. Краткий контекст инициативы.
5. Обязательные элементы документа.
6. Выявленные проблемы.

улучшения. Не подставляй имя файла вместо названия инициативы, если во входных
данных доступно содержательное название.

### Стадия инициативы

Выведи одну стадию, определённую парсером или явно переданную во входных
данных. Не определяй стадию повторно по отдельным фразам из аналитических
выводов и/или исходного документа.

Допустимые значения:

- Gate 1;
- Gate 2;
- Gate 3;
- Progress Review;
- Stream Review 1;
- Stream Review 2+;

Если для кейса во время загрузки документа стадия указана вручную, выбирай указанную вручную стадию, а не ту, которую определил автоматический парсер.

### Traction Summary

Информацию для этого раздела бери из Traction model или Financial model входного документа (обычно FAQ 3,4,6,7 или 8 основного документа); если там нет полной разбивки, используй таблицу текущего incremental P&L / output metrics в FAQ или приложении. Не смешивай текущий сценарий с предыдущим, альтернативным или строками ToBe / Diff vs previous IC, кроме узко проверенного переноса Revenue Total по правилу ниже.
Выведи total incremental Revenue и total incremental DTB с разбивкой по годам или кварталам, если они представлены в документе. Если есть обе метрики, покажи обе в отдельных таблицах, каждую со своими периодами, единицами измерения и Total из того же источника. Если есть только одна, покажи только её.
В первой строке каждой таблицы содержатся заголовок метрики (Revenue или DTB) и периоды. Последний столбец Total обязателен всегда, в обеих языковых версиях и в PDF/Word. Число Total бери только из итоговой ячейки той же метрики, текущего сценария и того же временного горизонта исходной таблицы документа защиты; не вычисляй сумму или среднее самостоятельно. Не смешивай разные временные горизонты: Total за 2026–2031 нельзя ставить под таблицей с периодами только 2026–2030. Узкое исключение для Revenue: если в выбранной инкрементальной таблице нет Total, проверь явно напечатанный Revenue Total в таблице ToBe P&L из FAQ или приложения. Используй его только когда период Total совпадает с периодами инкрементальной таблицы и **каждое** годовое значение Revenue в ToBe P&L численно совпадает с соответствующим значением выбранной таблицы. Не переносить такой Total при пропуске года, расхождении хотя бы одного значения, неоднозначных итогах или другом сценарии; для DTB это исключение не действует. Если в проверенной исходной таблице итоговой ячейки нет и исключение не сработало, напиши в ячейке Total «отсутствуют данные в документе защиты» (EN: «no data in the defense document»). Если исходную таблицу или итоговую ячейку не удалось надёжно извлечь, напиши «невозможно извлечь данные» (EN: «could not extract data»). Не подставляй число из другой таблицы без такой проверки.
Во второй строке содержится заголовок Total incremental output uplifts и значения соответствующей incremental метрики.
Если в нужной таблице исходного документа есть только одна строка с incremental, без указания, что она - Total, возьми её за итоговую строку метрики, но не подставляй её значения по годам в столбец Total.
Если в нужном разделе исходного документа есть несколько строк одной incremental метрики без строки Total, выведи все такие строки в таблице этой метрики.
Если в исходном документе есть строка Total для incremental Revenue или DTB, выведи для соответствующей метрики только её, не выводи входящие в нее строки.
Размер шрифта в пункте такой же, как в остальных пунктах, размер шрифта в таблице - на 2 кегля (пункта) меньше.
Никогда не выдумывай числа от себя. Если в выбранной таблице документа нет каких-то цифр, укажи причину в этой ячейке. Если данных нет в оригинальном документе, поставь - "Нет данных в документе". Если ты не уверен, есть ли данные в оригинальном документе или ты не смог спарсить данные из документа, поставь - "Не смог получить данные". Подстрой размер этого шрифта так, чтобы он помещался в ячейку.
В обеих таблицах выровни ширину ячеек, чтобы визуально они смотрелись органически - одна под другой без более широких или узких ячеек.
Пример структуры - НЕ ИСПОЛЬЗУЙ значения в этом примере и не подмешивай их к реальным выводам саммари.

Строка 1: "Output-метрики – uplifts", 2026, 2027, 2028, 2029, 2030, Total
Строка 2: "Revenue (incr)", 1, 3, 20, 61, 85, 180

### Краткий контекст инициативы

Дай понятное описание инициативы объёмом не более 6 предложений. Учти, что пользователь видит инициативу в первый раз и хочет идти от общего к частному.
Контекст должен позволить понять предмет инициативы до появления отдельных цифр и выводов по метрикам.

В разделе обязательно должны быть ответы на вопросы:
- Что это за инициатива, какую проблему она решает и как?
- Есть ли целевое видение продукта? Если есть, какое оно? Если такой информации нет, прямо напиши об этом, что в документе не представлено целевое видение продукта.
- На какой стадии находится инициатива сейчас?
- Какие пилоты проводились до этого/какие гипотезы проверялись, чтобы понять, что инициатива востребована? Если во входных данных есть эта информация, опиши, как это связано с итоговым образом продукта.
Обязательно проверь, что предложения соответствуют правилам русского или английского языка (в зависимости от языка). Не должно быть незаконченных предложений со странными формулировками.
Пример странной фрмулироки на русском языке: " Она решает три проблемы покупателя: **сложно выразить, что именно нужно**, релевантные ресейл-предложения теряются в общем поиске, и покупателю не хватает уверенности в товаре или продавце перед контактом." В выделенном жирном фрагменте не написано, кому что-то нужно. Такого быть не должно.
Не включай сюда цель встречи, формальный вердикт или рекомендации.

### Обязательные элементы документа

Выбери ровно один чеклист, соответствующий стадии инициативы. Не добавляй
другие критерии и не меняй формулировки пунктов.
В веб-версии не показывай поясняющий подзаголовок и разделительную линию перед первым элементом; линии между следующими элементами оставь. Текст подпунктов делай того же размера и цвета, что и текст доказательств. Статус каждого пункта и оцениваемого подпункта ставь после последнего слова с отступом в три пробела на той же строке; при недостатке ширины переноси вместе последнее слово и статус, но не отделяй статус от слова. В списках оцениваемых подпунктов сначала показывай все подтверждённые, затем все недостаточно подтверждённые, сохраняя исходный порядок внутри каждой группы. Заголовок таблицы метрик после списка commitments также отделяй вертикальным отступом.

Для каждого пункта, если в пункте не описано иное, выведи:
- точное название критерия;
- статус `Есть`, `Частично подтверждено` или `Нет` для русского языка,
`Present`, `Partially confirmed` или `Missing` соответственно для английского языка.
При оформлении документа подсвети статус `Есть` или `Present` зелёным цветом, `Частично подтверждено` или `Partially confirmed` — оранжевым, а статус `Нет` или `Missing` — красным цветом;
`есть` означает, что в Gate Challenger пункт отмечен зелёным и для него приведено доказательство.
`частично подтверждено` означает, что пункт отмечен жёлтым: он представлен, но доказательств недостаточно, в том числе если есть лишь заголовок доказательства или план, как мы это докажем.
`нет` означает, что пункт отмечен красным и отсутствует полностью.

- Краткое доказательство в 1-2 предложения статуса. Краткое доказательство формируй только на основании входных данных и ничего не придумывай от себя.
Краткое доказательство выводи в структуре. Что требовалось доказать, чем доказано, на основании чего доказано и почему считаешь это доказательством.

Для каждого элемента из этого раздела не вывод перед названием пункта какую-либо цветовую дифференциацию (например, кружок с цветом), Вместо этого пронумеруй кажыдй пункт (подпункты оставь без нумерации).


#### Gate 1

1. Market/opportunity sizing через бенчмарки или рыночные данные.
2. Хотя бы первичный traction, пусть с низкой confidence.
3. Набор гипотез для проверки до Gate 2, с метриками и thresholds.
В этом пункте выведи списком набор гипотез в формате:
Краткое описание гипотезы - условия, при которых считаем гипотезу подтвержденной.

#### Gate 2

1. Уникальное товарное предложение (УТП).
В этом пункте нужно в явном виде вывести краткое, в 1-2 предложения в чем представленный продукт улчше имеющихся на рынке и почему.
Не выдумывай данные и доказательства от себя, бери только информацию из входных источников.
"Есть" проставляется, если УТП явно считывается из текста, при этом не цепляйся к качеству этого УТП. Для этой стадии `Есть` ставится даже в том случае, если доказательства представлены просто бенчмарками и не опираются на реальные проверки.
2. Результаты проверки гипотез из Gate 1.
В заголовке этого пункта вместо дроби и цветного статуса выводи, в соответствии с правилами русского языка (числа, склонения): «Результаты проверки гипотез из Gate 1: X гипотезы(гипотеза для 1 штуки) из Y подтверждены, Z гипотезы (гипотеза для 1 штуки) из Y недостаточно подтверждены.» Здесь Y — количество всех выведенных ниже гипотез, X — количество с вердиктом `confirmed`, Z — количество с вердиктом `insufficient`; X + Z = Y. Удаляй дублирующиеся тезисы до подсчёта; не выдумывай число при пустом списке. Техническое поле `status` оставь в формате X/Y для совместимости с текущим JSON-контрактом, но не показывай эту дробь рядом с заголовком, если есть подробный список.
    В этом подпункте выведи  пункты простым маркированным списком
Формат:
"Номер пунтка", "гипотеза/проблема/тезис из IC Review и Gate Challenger", "Вердикт (Сonfirmed или Not sufficiently confirmed. ## Технический формат результата

Сам скилл остаётся обычным Markdown-файлом. Верни данные в соответствии с
переданной JSON Schema `new-summary.schema.json`; схема нужна только приложению
для надёжного сохранения и отображения разделов.

Правила заполнения технических полей:

- `schema_version` всегда равно `new-summary-v2`;
- `language` равно `en`, потому что первая версия Summary по текущему языковому
  контракту всегда английская;
- `title` всегда строится по формату `AI Summary <название инициативы>`;
- `versions` содержит ровно две полные версии Summary: первой идёт английская
  версия, второй идёт русская версия;
- каждый объект в `versions[]` содержит `language`, `stage`, `context`,
  `traction_summary` и `required_elements`; `critical_problems` может быть
  пустым массивом или отсутствовать; не создавай отдельные `confirmed`,
  `insufficiently_confirmed`, `other` или `document_quality_percent`;
- `versions[].traction_summary.tables[]` содержит отдельную таблицу для каждой доступной метрики Revenue и DTB; не добавляй отсутствующую метрику;
- каждая таблица содержит `metric`, `metric_label`, `periods` и `rows`; `metric` равно `revenue` или `dtb`;
- `periods` содержит заголовки годов, кварталов и обязательный последний столбец Total именно для этой метрики и её горизонта, в порядке вывода в PDF;
